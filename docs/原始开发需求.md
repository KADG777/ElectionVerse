# ElectionVerse：基于 Godot 4 与 Qwen 的多 Agent 市长选举游戏

## 0. 你的角色与开发目标

你是一名精通 Godot 4、GDScript、LLM API 接入、游戏状态管理和多智能体系统设计的高级游戏开发工程师。

请直接在当前工作目录中创建一个**完整、可以通过 Godot 编辑器打开并运行的 2D 游戏项目**。

项目名称：**ElectionVerse：青岚镇市长选举**

这个项目是 StoryVerse 多 Agent 动态叙事游戏的最小原型。

本次开发的重点不是精致的美术效果，而是验证：

1. 多个 NPC 是否能够表现出不同的人格、目标和偏好。
2. NPC 是否拥有独立的历史记忆。
3. 玩家与 AI 候选人的不同言论是否能改变居民评价。
4. 居民是否能够依据个人利益、历史经历和信息认知自主投票。
5. 整个游戏过程是否能够通过结构化事件日志进行追踪。
6. Qwen API 是否可以稳定接入 Godot 并由玩家自行配置。
7. 没有 API Key 时是否可以通过 Mock 模式完整游玩。

请直接实现功能、创建文件并尽可能执行测试，不要仅仅输出设计方案。

## 1. 技术栈与约束

- 游戏引擎：Godot 4.x 稳定版。
- 编程语言：GDScript。
- UI：Godot 内置 Control 节点。
- HTTP：Godot 内置 HTTPRequest。
- LLM：阿里云百炼 Qwen API。
- 数据存储：JSON + Godot user:// 目录。
- 项目采用模块化结构。
- 不使用 Python、Streamlit、React 或外部后端。
- 不依赖收费 Godot 插件。
- 所有游戏界面使用简体中文。
- 优先支持 Windows 桌面运行。
- 如果没有美术素材，使用 Godot 自带形状、ColorRect、PanelContainer 等组件完成清晰、美观的界面。
- 代码应具有类型标注、关键逻辑注释、错误处理和测试。

不要求制作自由探索的大型地图。第一版采用可交互的市政厅与居民管理面板。

## 2. 游戏背景

游戏发生于虚构的现代小镇“青岚镇”。

现任市长即将卸任，玩家与 AI 候选人竞争新一任市长。

青岚镇有 7 名具有投票权的居民。

每名居民具有不同的社会背景、利益诉求、人格特点和人际关系。

玩家需要通过公开演讲、政策表态和突发事件处理争取选票。

AI 竞争对手会根据当前局势和自己的性格主动提出政策、批评玩家或争取居民支持。

游戏共进行 3 轮，每轮发生一件公共事件。

三轮结束后，居民独立进行最终投票，获得更多选票的候选人获胜。

核心设计要求：

**选举结果必须由角色状态、历史事件和决策机制产生，不能简单让模型随机指定获胜者。**

## 3. 游戏角色设计

### 3.1 玩家候选人

玩家可以设置姓名，默认名称为“玩家”。

每轮可针对当前事件输入一段自然语言演讲或行动方案。

示例：

“我支持建设工厂，但要求企业先通过第三方环保评估，同时必须保障本镇居民的就业机会。”

不应只允许玩家选择预设的 A/B/C 选项。

但为了降低开发难度，可额外提供三个快捷选项：

- 支持
- 反对
- 提出折中方案

选择快捷选项后自动填充文本框，玩家仍可修改。

### 3.2 AI 候选人

姓名：陈远

人物设定：

- 42 岁
- 前镇议会议员
- 理性、善于表达
- 具有较强竞争意识
- 注重经济发展和社会秩序
- 会根据民意调整宣传策略
- 有时可能为了争取支持而作出不受欢迎的妥协

AI 对手拥有独立的 AgentState、Personality、Memory 和 Goals。

每轮玩家提交方案后，由 Qwen 为陈远生成本轮立场、公开发言以及可执行的行动建议。

行动必须经过游戏规则引擎验证。

AI 对手不能直接修改居民选票或支持度。

### 3.3 七名居民 Agent

**居民 1：林老师**

- 职业：小学教师
- 性格：理性、温和、具有责任感
- 关注：教育、公共服务、儿童福利
- 特征：偏好长期稳定的政策，反感空洞承诺

**居民 2：周师傅**

- 职业：工厂技术工人
- 性格：直率、固执、重视家庭
- 关注：就业、收入、劳动保障
- 特征：倾向相信能够改善生活的实际措施

**居民 3：许医生**

- 职业：社区医生
- 性格：谨慎、专业、坚持原则
- 关注：公共卫生、环境健康、医疗条件
- 特征：非常重视证据和潜在风险

**居民 4：苏晴**

- 职业：大学毕业后返乡创业者
- 性格：活泼、开放、有冒险精神
- 关注：创新、青年机会、数字经济
- 特征：容易欣赏新颖大胆的政策，但讨厌缺乏执行方案的口号

**居民 5：王奶奶**

- 职业：退休居民
- 性格：保守、重感情、记忆力好
- 关注：养老、社区安全、生活成本
- 特征：更相信长期积累的信誉，容易受熟人经历影响

**居民 6：赵老板**

- 职业：本地超市经营者
- 性格：精明、现实、善于观察
- 关注：税收、商业环境、基础设施
- 特征：优先考虑商业利益，但也重视候选人信誉

**居民 7：李记者**

- 职业：地方媒体记者
- 性格：好奇、敏锐、追求事实
- 关注：政府透明度、程序公平、信息公开
- 特征：反感掩盖事实，对前后矛盾的政策表态十分敏感

每个居民都应有自己的独立数据结构和 Prompt。

不能仅仅在 UI 中给七个角色换名字，实际却共用同一份记忆和立场。

## 4. NPC Agent 数据结构

每个 NPC 应包含以下信息：

```json
{
  "id": "npc_teacher",
  "name": "林老师",
  "role": "resident",
  "personality": {
    "traits": ["理性", "温和"],
    "risk_tolerance": 0.3,
    "openness": 0.6
  },
  "priorities": {
    "education": 0.9,
    "economy": 0.4,
    "environment": 0.6,
    "health": 0.5,
    "transparency": 0.7
  },
  "relationships": {
    "player": 0,
    "opponent": 0
  },
  "memories": [],
  "opinions": {
    "player": 50,
    "opponent": 50
  },
  "current_intention": "观察双方政策",
  "vote": null
}
```

要求：

- opinion 取值范围为 0–100。
- 每个居民对两位候选人的评价独立维护，不要求两者之和为 100。
- 关系、政策评价、信任和最终投票偏好不应全部混为一个变量。
- 角色人格应保持长期稳定。
- 历史事件可以改变角色评价，但不能随意覆盖原始人格。
- 对每轮的评价变化记录原因。
- 不允许模型直接指定任意支持度变化数值。

## 5. 游戏三轮事件

### 第一轮：工厂扩建争议

外部企业计划在青岚镇建设新工厂。

优点：

- 可以增加就业
- 可能带动地方税收
- 有利于经济发展

风险：

- 可能造成环境污染
- 居民对环保承诺缺乏信任
- 可能增加交通压力

玩家与 AI 对手分别提出解决方案。

不同居民根据各自关注的问题进行评价。

### 第二轮：学校资金分配

镇政府拥有有限的公共预算。

学校希望改善教学设备，但部分居民更关注养老与医疗设施。

玩家需要在有限预算条件下提出分配方案。

游戏应识别玩家方案是否符合预算约束。

不得允许候选人无代价地满足所有需求。

### 第三轮：突发暴雨与道路损坏

暴雨导致镇中心桥梁部分损坏。

居民需要快速恢复交通，同时担心维修质量与财政支出。

玩家和对手分别提出应急方案。

部分居民更重视速度，部分居民更重视安全与成本。

允许不同方案在不同居民心中产生不同效果。

每轮必须形成：

- 事件记录
- 玩家言论
- AI 对手言论
- 各居民反应
- 支持度与信任变化
- 更新后的 NPC 记忆
- 新的全局世界状态

## 6. 核心游戏流程

游戏启动：

主菜单 → 新游戏 → API 配置或 Mock 模式 → 创建居民 → 进入第一轮。

每轮执行以下流程：

### Step 1：展示公共事件

显示事件名称、背景、问题与已知约束。

### Step 2：玩家行动

玩家输入自然语言演讲或解决方案。

必须具有提交按钮。

限制空输入和过长输入。

### Step 3：AI 对手行动

调用 Qwen，生成 AI 候选人的立场与发言。

AI 对手应根据当前事件、此前政策和居民舆论形成自己的行动。

不得始终选择与玩家相反的立场。

### Step 4：居民评价

每名居民根据以下信息独立评价：

- 自身职业与利益
- 性格与价值观
- 玩家提出的方案
- AI 对手提出的方案
- 该居民能够得知的历史事件
- 对两位候选人的既有认知
- 双方承诺的一致性

由 Qwen 输出居民的文字反应、关注点、事实判断及倾向变化理由。

由确定性游戏规则计算最终数值更新。

### Step 5：更新关系与记忆

存储居民当轮评价及相关事件。

每个居民仅能访问自己有权知道的事件。

### Step 6：展示结果

游戏展示：

- 七名居民的当前评价
- 支持率变化
- 居民评论
- 本轮关键变化
- AI 对手发言
- 历史事件日志

然后允许玩家进入下一轮。

### Step 7：最终投票

第三轮结束后进行投票。

每个居民根据以下因素形成投票决定：

- 对两位候选人的最终政策评价
- 历史信任
- 重要议题权重
- 关键事件记忆
- 候选人承诺一致性

允许少量由固定种子控制的个体不确定性。

最终投票必须可解释、可复现。

在相同输入状态和随机种子下，确定性计票结果必须一致。

最终展示：

- 每名居民的选票
- 居民投票原因
- 最终票数
- 获胜候选人
- 游戏结果总结

## 7. Qwen API 接入

### 7.1 游戏内 API 设置

创建 API 设置页面，提供：

- API Key 输入框，使用密码模式隐藏内容
- API Base URL 输入框
- 模型名称输入框
- 测试连接按钮
- 保存本次会话配置按钮
- Mock 模式开关

示例配置：

```text
Provider: Qwen / Alibaba Cloud Bailian
API Base URL:
https://dashscope.aliyuncs.com/compatible-mode/v1

Model:
qwen-plus

API Key:
由用户自行填写
```

Base URL 必须允许修改，以兼容百炼不同地域或业务空间的 API 接入地址。

### 7.2 请求实现

使用 Godot HTTPRequest 节点。

按以下格式发起 POST 请求：

```http
POST {BASE_URL}/chat/completions
Authorization: Bearer YOUR_API_KEY
Content-Type: application/json
```

请求正文采用 OpenAI Chat Completions 兼容格式：

```json
{
  "model": "qwen-plus",
  "messages": [
    {
      "role": "system",
      "content": "你是青岚镇的一名居民，请根据个人记忆和利益判断候选人的政策。"
    },
    {
      "role": "user",
      "content": "玩家提出建设工厂，但要求先通过环保评估。请给出反应。"
    }
  ],
  "stream": false
}
```

从响应的 `choices[0].message.content` 提取模型正文。

解析失败时展示合理错误信息。

所有 API 请求必须采用异步执行，不能阻塞游戏 UI。

不要在同一个 HTTPRequest 节点上并发提交多个请求。

可以使用请求队列或独立 HTTPRequest 实例处理并发。

### 7.3 输出结构

要求 Agent 以 JSON 输出：

```json
{
  "npc_id": "npc_teacher",
  "reaction": "我支持发展经济，但不希望孩子们的健康成为代价。",
  "reasoning_summary": "方案考虑了环境风险，但缺少具体监管措施。",
  "evaluation": {
    "economy": 0.3,
    "environment": 0.8,
    "education": 0.2,
    "transparency": 0.6
  },
  "trust_signal": 0.2,
  "memory_summary": "玩家承诺建设工厂前开展环保评估。"
}
```

`evaluation` 取值范围为 -1 到 1，表示居民对当前方案在相关维度的主观评价，而非最终选票。

`trust_signal` 同样限制在 -1 到 1。

游戏规则引擎根据角色权重、当前状态、事件信息和评价结果计算具体变化。

必须校验模型输出的 JSON Schema、字段类型与取值范围。

如果 JSON 格式错误，允许一次纠正性重试。

重试失败则使用 Mock 评价并记录降级事件。

不得直接执行模型生成的代码，也不能将模型输出的任意字段作为可信状态修改指令。

### 7.4 API 安全

- 不在代码中硬编码 API Key。
- 不把 Key 写进默认项目配置文件。
- 不提交任何真实凭据。
- API Key 默认仅保留在当前运行进程的内存中。
- 如需本地长期保存凭据，须单独设计安全存储机制并明确提示风险。
- 日志不得包含 Key 或完整 Authorization 请求头。
- 第一版定位为本地桌面 Demo，不实现公开 Web 部署。
- 如果未来发布给其他用户使用，应改为通过受保护的服务端代理调用 Qwen。

## 8. NPC 评价与投票算法

不要把角色投票直接交给语言模型输出 0 或 1。

采用“LLM 主观评价 + 确定性状态更新”的混合架构。

对每位候选人维护独立的政策评价向量。

示例计算思想：

```text
policy_impact =
    sum(
        resident_priority[i]
        * agent_evaluation[i]
        * event_importance[i]
    )

opinion_delta =
    policy_impact * scale
    + trust_effect
    + consistency_effect

new_opinion =
    clamp(old_opinion + opinion_delta, 0, 100)
```

需在代码中明确每一项的含义、系数与范围。

为了避免极端变化：

- 单次事件造成的评价变化需要上限。
- 重大事件允许较大变化。
- 角色长期信任不应被普通小事件瞬间清零。
- 对所有候选人适用同一套规则。
- 不要为玩家额外加分。
- 不要为 AI 对手添加隐形惩罚。

最终投票可比较居民对两名候选人的综合得分，并在必要时通过固定随机种子模拟有限的不确定性。

居民投票后的自然语言解释可以由 Qwen 生成，但实际票数必须以游戏规则引擎的结果为准。

## 9. 游戏 UI 设计

整体风格：

- 现代化 2D 独立游戏
- 温暖的小镇配色
- 干净、易读的卡片 UI
- 合理的排版与间距
- 支持 1280 × 720 起步分辨率
- 窗口缩放时布局正常

主界面布局：

左侧：事件区域

- 当前轮次
- 公共事件背景
- 玩家演讲文本框
- 提交行动按钮

中间：选举区域

- 玩家候选人
- AI 对手候选人
- AI 对手本轮发言
- 本轮事件反馈

右侧：居民区域

- 七名居民卡片

- 事件历史

游戏结束后显示独立的计票结算界面。

## 10. Agent 记忆与事件日志

采用结构化事件记录系统。

每轮产生事件 ID。

每条重要事件保存：

```json
{
  "event_id": "event_001",
  "round": 1,
  "type": "candidate_statement",
  "actor_id": "player",
  "content": "支持工厂建设，但要求严格环保评估",
  "visible_to": ["all"],
  "effects": [],
  "timestamp": 1
}
```

NPC 记忆至少区分：

1. 角色人格与固定背景
2. 角色亲历或获得的信息
3. 角色对事件的主观评价
4. 重要历史摘要

要确保居民 Agent 不会无缘无故知道没有接收到的信息。

保留最近重要事件和摘要，避免每次调用 Qwen 都发送全部历史对话。

游戏事件存储在独立的 EventLog 模块中。

所有角色状态更新应由 GameManager 或 WorldState 执行，Agent 不允许自行直接修改全局世界状态。

## 11. Demo 模式和成本控制

提供两种运行方式。

### Mock 模式

- 不需要 API Key。
- 使用预定义居民反应模板和固定性格权重。
- 使用同一套规则引擎计算评价与投票。
- 支持完整运行三轮选举。
- 支持固定随机种子。
- 用于自动化测试、演示和离线开发。

### Qwen 模式

- AI 对手调用 Qwen 生成行动。
- 七位居民根据独立上下文调用 Qwen。
- 每轮完成必要的 Agent 更新。
- 对单次调用设置超时。
- 显示模型执行进度。
- 失败时允许重试或降级到 Mock 模式。
- 严格避免无限 Agent 自主对话。

第一版不需要让所有 Agent 每秒自动行动。

采用“事件触发 Agent 更新”的方式，避免成本失控。

提供基础调用统计：

- 调用次数
- 输入 Token
- 输出 Token
- 请求耗时
- 失败与重试次数

如果 API 未返回 Token 用量，标记为“未提供”，不能伪造统计数字。

## 13. 游戏规则与状态管理

必须实现有限状态机：

```text
MAIN_MENU
    ↓
CONFIGURATION
    ↓
ROUND_INTRO
    ↓
WAITING_PLAYER_ACTION
    ↓
AI_OPPONENT_TURN
    ↓
RESIDENT_EVALUATION
    ↓
ROUND_RESULT
    ↓
NEXT_ROUND
    ↓
FINAL_VOTE
    ↓
GAME_OVER
```

只有合法状态才允许执行对应操作。

在居民评价阶段禁止玩家重复提交行动。

Qwen 请求失败必须恢复至明确的可操作状态。

存档至少保存：

- 当前轮次
- 玩家候选人名称
- AI 候选人状态
- 全部居民状态
- 历史事件
- 当前阶段
- 随机种子

不允许在读取存档后重新触发已经成功提交的历史事件，导致评价重复增加。

## 14. 自动化测试要求

至少实现以下测试：

**测试 1：居民差异性**

相同政策输入下，两个具有不同利益权重的居民可以产生不同的政策影响分数。

**测试 2：状态更新**

同一事件只应被应用一次。

评价必须限制在 0–100。

**测试 3：记忆隔离**

角色只能获取自己有权访问的事件。

**测试 4：投票规则**

给定完全一致的居民状态和随机种子，两次计票结果必须相同。

**测试 5：API 解析**

正常 JSON 可以正确解析。

无效 JSON、缺失字段和超出范围的数值必须被拒绝或安全处理。

**测试 6：失败恢复**

模拟 Qwen 超时或失败时，游戏不会崩溃，玩家可以重试或选择 Mock 降级。

**测试 7：完整流程**

在 Mock 模式下可以完成三轮选举、输出最终结果并保存完整事件记录。

测试必须能够在 Godot 中执行，建议支持 headless 测试运行。
